## Why We're Doing This

### Qualified Problem

**For:** Sea technical/operations audience.
**Who:** want to understand not only what the demo tool does, but how AI could help build it.
**The:** current demo section proves Ocean USB Builder exists, but it jumps quickly from guardrails into the finished tool and anatomy.
**That:** leaves a storytelling gap around requirement discovery, technology choices, architecture boundaries, verification and human approval gates.
**Unlike:** adding more dense text into the live demo slide, this change gives the build journey its own presenter-friendly slide.
**Our approach:** add one new slide before the live demo: problem -> goal -> stack -> architecture -> verification.

1. **Product:** the audience asked for practical demo/case content, so they need the origin story, not only the final UI.
2. **Technical:** the OSDCloud repo contains real evidence of stack and architecture decisions that are not visible enough in the deck.
3. **Design:** The prior demo/anatomy slides were already doing two jobs: safe live walkthrough and architecture anatomy. Adding process detail there would make both harder to present.

### Impact If Not Addressed

- Audience may think "AI built an app" is magic instead of a disciplined workflow.
- Presenter has fewer cues to explain how to turn an operational pain point into an AI-agent task.
- The demo may feel like a finished artifact instead of proof of the playbook.
